> 문서 역할: 장애 버전 배포를 감지하고 이전 정상 버전으로 복구하는 Week3 구현 계획을 정리한다.

# Week 3 — Failure Recovery & Rollback 설계 및 구현 계획

이 문서는 [Week2](Week2.md)의 Rolling 배포를 확장하는 3주 차 설계다. 기존 Week2의 장애 주입·자동 복구·상태 영속화·순차 롤백 설계를 이 문서로 이동했다. 아직 구현 또는 실행 완료 결과가 아니다.

## 1. 목표와 과제 대응

Week2에서 정상 배포한 **v2**를 기준으로 장애가 있는 **v3**를 배포한다. 장애를 감지하면 후속 배포를 중단하고 이전 정상 **v2**로 복구하며, 직접 요청과 Nginx 경유 요청으로 정상 처리를 확인한다.

| 과제 | 설계 | 증거 |
| --- | --- | --- |
| 장애 재현 | 지정 서버의 새 v3에 readiness 실패 또는 실행 실패 주입 | 장애 조건·서버·릴리스·로그 |
| 장애 감지 | Jenkins 실패 결과와 Ansible 검사·실패 처리 연결 | 탐지 시각·실패 task·후속 서버 미배포 |
| 자동 롤백 | 실패 서버의 이전 이미지와 실행 설정 복원 | 복원 이미지 ID·버전·서버별 이벤트 |
| 복구 검증 | health·ready·실제 응답·릴리스 및 LB 경유 확인 | v2 정상 응답·요청 성공률·복구 시간 |

단일 LB 자체의 고가용성과 DB 마이그레이션은 범위에 포함하지 않는다. 정리 자동화와 Galaxy 도입은 [선택 확장](deployment-extensions.md)으로 분리한다.

## 2. 장애 시나리오와 주입 방법

실험용 옵션으로 시작 지연, readiness 실패, 애플리케이션 실행 실패, 일정 시간 후 `/`의 503 응답을 추가한다. 기본값은 정상이며 지정한 대상 서버의 새 v3 컨테이너에만 적용한다. 공개 장애 제어 API는 만들지 않는다. 다른 스터디원의 컨테이너나 공용 Nginx를 중지하지 않는다.

배포 전 이미지 검사에서 실패한 경우는 배포 차단 실험이며 원격 롤백 검증으로 집계하지 않는다. 원격 롤백 실험은 이미지 검사를 통과한 동일 이미지에 대상 서버 전용 장애 옵션을 적용해 재현한다. 일반 배포의 이미지 검사를 비활성화하지 않는다.

| 실험 | 기대 결과 |
| --- | --- |
| 첫 대상 app1의 v3 readiness 실패 또는 실행 실패 | app1을 v2로 자동 복구, app2·app3 미배포, 전체 v2 정상 처리 |
| app1 성공 후 app2의 v3 readiness 실패 | app2는 v2로 복구, app3 미배포, app1은 v3로 남아 부분 실패 표시 |
| 새 버전의 잘못된 릴리스 | 재등록 전 차단, 이전 정상 버전 복구 |
| LB에서 대상 포트 접근 불가 | 서버 내부 검사 성공과 관계없이 재등록 차단 |
| 다른 서버가 이미 장애 | 추가 서버 제외 금지 |
| 긴 요청으로 drain 기한 초과 | 앱 강제 종료 없이 중단, 기존 앱 정상 확인 후 재등록 |
| 재등록 후 서비스 503 | 대상 재제외·drain·v2 복구, 다음 서버 중단 |
| 잘못된 Nginx 후보 설정 | reload 금지, 기존 정상 설정 보존 |
| 배포 중단 후 재실행 | 실제 상태 대조, 잘못된 교체·등록 금지 |
| 전체 이전 버전 복귀 | v3로 갱신된 서버를 한 대씩 v2로 복원 |

기본 제출 실험은 첫 대상에서 실패시켜 전 서버 v2 복구를 확인한다. 부분 배포 실험에서는 실패 서버 복구와 전체 롤백을 구분하고, 전체 복귀가 필요하면 별도 순차 rollback 경로로 완료한다. 재등록 후 장애 실험은 오류 0건보다 탐지·복구 성공과 복구 시간을 평가한다.

## 3. Jenkins·Ansible 확장

Week2의 이미지 준비·트래픽 제외·drain·검증 흐름을 재사용한다. Preflight에서 서버별 이전 정상 이미지 ID·태그·환경·포트·재시작 정책과 LB 구성을 보존하고 복구 가능성을 확인한다. 이전 정상은 가장 큰 빌드 번호가 아니라 검증된 실제 릴리스로 판단한다.

| 파일/구간 | 추가 책임 |
| --- | --- |
| `playbook/prepare.yml` | 이전 정상 이미지·정확한 실행 설정·복구 자원 확인 |
| `playbook/deploy.yml` | `block/rescue`로 현재 실패 서버 자동 복구 후 명시적 실패 반환 |
| `roles/deployment_state/` | 상태 영속화와 재실행 시 실제 서비스 대조 |
| `playbook/rollback.yml` | 지정 서버 또는 이미 갱신된 서버들의 순차 복구 |
| `roles/verification/` | 롤백 후 이전 정상 릴리스·health·ready·서비스 검사 |
| Jenkins `post` | 원래 배포 실패와 복구 성공/실패를 별도 기록하고 증거 보관 |

서버 복구는 Ansible에서 처리한다. Jenkins `post`에서 무조건 대상을 재등록하거나 전체 롤백하지 않는다. 복구가 성공해도 배포 job은 실패로 남기고 다음 서버로 진행하지 않는다. 같은 job의 직렬화를 유지하며 별도 복구 job을 도입하면 공통 환경 잠금을 먼저 마련한다.

## 4. 서버별 상태와 실패 처리

### 4-1. 상태 기록

LB의 프로젝트 전용 경로(예: `/var/lib/sohyeon-cicd/deployment.json`)에 상태를 원자적으로 기록한다. Jenkins workspace에만 두지 않는다.

```yaml
deployment_id: v3-a1b2c3d4e5f6-42
target_release: v3-a1b2c3d4e5f6-42
status: rolling
excluded_hosts: []
servers:
  sohyeon-app1:
    current_release: v3-a1b2c3d4e5f6-42
    previous_release: v2-112233445566-41
    phase: healthy
  sohyeon-app2:
    current_release: v2-112233445566-41
    previous_release: v2-112233445566-41
    phase: pending
  sohyeon-app3:
    current_release: v2-112233445566-41
    previous_release: v2-112233445566-41
    phase: pending
```

상태는 `pending → draining → updating → verifying → rejoining → healthy`로 기록한다. 서버의 previous_release와 실행 설정은 해당 배포 시작 시 스냅샷으로 고정하여 재시도 때문에 덮어쓰지 않는다. 전체 성공은 세 서버가 목표 릴리스이며 제외 대상이 없을 때만 확정한다.

재실행 시 상태 파일, 실제 컨테이너 이미지·응답, Nginx 설정·실제 서비스 상태를 대조한다. 파일만 보고 배포 완료나 트래픽 제외 완료를 가정하지 않는다. 불일치는 `recovery_required`로 표시하고 자동 교체를 멈춘다. `run_once`는 serial 배치마다 실행될 수 있으므로 전체 상태 초기화는 별도 preflight play에서 한 번 수행한다.

### 4-2. 실패 위치별 처리

| 실패 | 처리 | 다음 서버 |
| --- | --- | --- |
| 이미지 테스트·전달·preflight 실패 | 기존 서비스 유지, 배포 시작 안 함 | 진행 금지 |
| Nginx 제외 실패 | 기존 컨테이너 보존, 설정·서비스 확인 | 진행 금지 |
| drain 시간 초과 | 기존 앱 정상 확인 후 재등록, 실패 기록 | 진행 금지 |
| 새 컨테이너 실행·직접 검증 실패 | 제외 상태에서 이전 이미지·실행 설정 복원 후 검증·재등록 | 진행 금지 |
| 재등록 후 대상 장애 | 다시 제외·drain 후 이전 버전 복구, 검증·재등록 | 진행 금지 |
| 이전 버전 복구 실패 | 대상 제외 유지, 나머지 두 대 확인, 복구 자료 보존 | 진행 금지 |
| SSH 단절·Jenkins 중단 | 확실하지 않은 대상을 자동 등록/삭제하지 않음, 상태 대조 필요 | 진행 금지 |
| 최종 전체 검증 실패 | 새 배포 중단, 문제 서버 식별 및 복구 | 진행 금지 |

기본 자동 복구 범위는 **현재 실패한 서버**다. 예를 들어 app1이 v3로 성공한 뒤 app2가 실패하면 app2를 v2로 복구하고 app3는 v2로 유지한다. app1은 v3로 남으므로 전체 상태를 `failed_partial`로 기록한다. 이것을 전체 롤백 성공이라고 보고하지 않는다.

전체 v2 복귀가 필요하면 이미 갱신된 서버들을 동일한 제외·drain·복원·검증·등록 절차로 한 대씩 되돌리는 별도 rollback 경로를 실행한다. 모든 서버를 동시에 복원하지 않는다. 이 정책 때문에 구·신버전 공존 가능성이 사전 조건이다.

Ansible `block/rescue`에서 복구 후에도 `ansible.builtin.fail`로 원래 배포 실패를 반환한다. unreachable과 프로세스 중단은 일반 rescue의 완전한 보장 범위가 아니므로 영속 상태와 별도 복구 경로가 필요하다. [Ansible Blocks 문서](https://docs.ansible.com/projects/ansible-core/devel/playbook_guide/playbooks_blocks.html)

## 5. 복구 검증과 실행 결과 기록

Week2의 연속 요청 도구를 장애 발생 전부터 복구 후 최소 60초까지 실행한다. Agent 유실 등으로 관측이 끊기면 실제 누락 구간을 기록한다. 표본의 연속 실패 구간을 정확한 전체 장애 시간이라고 표현하지 않는다.

- 장애 조건, 대상 서버, v3와 이전 정상 v2의 이미지 ID·릴리스를 기록한다.
- 장애 발생·탐지·복구 시작·복구 검증 완료 시각을 UTC로 기록한다. 탐지 시간은 탐지−발생, 복구 소요는 복구 완료−탐지로 산출하고 기준을 명시한다.
- 복구 서버의 `/health`, `/ready`, `/`, `/version`, 서버 ID와 기대 v2 릴리스를 확인한다.
- LB에서 대상 서버로 직접 요청하고 재등록 후 해당 서버의 실제 처리 기록과 LB 안정화를 확인한다.
- app2 실패 실험에서는 app3가 미배포 상태인지, app1의 v3 잔존이 부분 실패로 기록됐는지 확인한다.
- 전체 롤백 완료 판정은 전 서버가 v2이며 제외 대상이 없고 LB 서비스도 정상일 때만 한다.
- 요청 원본·집계·컨테이너 로그·Ansible 로그·서버별 이벤트·민감값을 제거한 상태 기록을 Jenkins 아티팩트로 보관한다. 복구용 원본 실행 설정은 원격 접근 제한 경로에 보존한다.
