BOOTSTRAP은 기존 Week1 앱을 v1으로 전환할 때 사용하는 옵션이다. 다만 **#24 시작 시점에는 이미 #22의 v1 릴리스가 세 서버에서 응답하고 있었다.** 따라서 #24는 Week1 앱을 처음 교체한 기록이 아니라, BOOTSTRAP을 켠 상태에서 v1 재배포부터 정리까지 전체 파이프라인을 성공시킨 기록이다. #25는 그 결과를 기준으로 실제 v1→v2 전환을 수행했다.

## 3. #24 — v1 + BOOTSTRAP 성공 과정

10:08:12부터 저장소 파일과 실행 환경을 확인하고 Ansible 컬렉션 및 Docker 사용 가능 여부를 검사했다. 단위·통합 테스트는 **50개 모두 통과**, 테스트 실행 시간은 **47.011초**였다.

이어서 `sohyeon-cicd-app:v1-e2cbef6dde5b-24` 이미지를 빌드했다. 임시 테스트 컨테이너에서 버전과 릴리스 응답을 검사한 후 해당 컨테이너를 정리하고, 검증된 이미지를 `image.tar`로 저장했다. 전송용 체크섬과 릴리스 정보도 생성했다.

### 3.2 배포 준비

10:09:05~10:09:36에 다음 작업을 수행했다.

1. 인벤토리 대상의 SSH 키를 수집해 작업 전용 `known_hosts`를 준비했다.
2. 앱 서버의 프로젝트 작업 디렉터리와 정리 도구를 확인했다.
3. 기존 컨테이너의 소유권·이름·포트를 확인하고, LB에서 현재 서비스 응답을 검사했다.
4. 복구에 사용할 이전 이미지와 컨테이너 설정을 보존했다.
5. 저장 공간을 확인하고 검증된 이미지 tar를 세 서버에 전송했다. 이미지의 태그·라벨을 검사한 뒤 로드하고, 전송한 tar를 제거했다.
6. 세 서버의 준비 완료를 확인한 후 LB 도구와 기존 Nginx 설정·서비스를 검사했다. 기존 정상 설정을 보존하고 프로젝트 설정을 검증했다.

이미지 준비 단계에서는 실행 중인 앱 컨테이너를 교체하지 않았다.

### 3.3 서버별 롤링 진행

10:09:36부터 LB 주소에 30초간 기준 요청을 보낸 후 롤링을 시작했다. 각 서버는 다음 순서로 처리했다.

1. 다른 앱 서버가 요청을 처리할 수 있는지 확인한다.
2. 현재 대상 한 대를 Nginx upstream에서 제외하고 설정 검사 후 reload한다.
3. 기존 Nginx 워커가 요청 처리를 마치고 앱 포트의 활성 연결이 사라질 때까지 기다린다.
4. 소유권을 다시 확인한 뒤 해당 컨테이너를 정상 종료·제거하고, 검증된 이미지로 새 컨테이너를 시작한다.
5. 새 앱의 상태·서버 식별자·릴리스를 확인한 뒤 upstream에 복귀시킨다.
6. Nginx를 통해 새 릴리스가 실제 응답하는지 확인하고 안정성 관측을 마친 후 다음 서버로 진행한다.

| app2 | 10:11:21~10:11:51 | #24 v1 교체 및 LB 복귀 |

## 5. 실행 결과의 의미

#24는 v1 배포·가용성 측정·정리까지 전체 흐름을 성공시켰고, #25는 그 v1을 기준으로 세 서버를 v2로 순차 교체했다. 두 실행 모두 측정 요청의 실패와 수집 오류가 없었으며, 배포 및 정리 후 최종 서비스 검사도 통과했다. 이는 **해당 관측 구간과 요청에서 서비스 중단이 관측되지 않았음**을 의미한다.

정리 로그에 나타난 대상은 `sohyeon-cicd-app`의 특정 이전 이미지와 프로젝트 Nginx 백업·후보 파일이다. 다른 프로젝트 전체나 Docker 전체를 일괄 삭제한 기록은 없다. 다만 Nginx reload는 공유 Nginx 프로세스에 적용되는 작업이므로, 이 로그만으로 다른 모든 프로젝트의 무영향까지 입증한 것은 아니다.

두 로그의 Python 인터프리터 탐색 및 Ansible facts 관련 경고는 실행 실패로 이어지지 않았다. 접근 로그 회전 정책의 실제 적용 여부는 이 두 성공 로그만으로는 확인되지 않는다.
