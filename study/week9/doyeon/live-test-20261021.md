# 2026-10-21 카나리 → 롤링 배포 및 롤백 실검증

모든 시각은 한국 시간(KST, UTC+9)이다. 대상은 도연 앱 VM 3대와 개인 Nginx 설정(`/etc/nginx/conf.d/doyeon.conf`, 포트 18005)이다. 실행은 로컬 Ansible에서 수행했다. [설계와 실행 방법](README.md), [Timeout·Retry·Backoff·Jitter 학습 정리](01-timeouts-retries-backoff-jitter.md)를 함께 참고한다.

## 사전 상태와 준비

- 앱1·앱2·앱3의 직접 `/health`는 모두 `v2-8`, `status=ok`였다. LB `/health`도 `v2-8`로 응답했다.
- Nginx 개인 upstream에 서버 3대가 모두 기본 가중치로 활성화돼 있었고 `nginx -t`가 통과했다.
- `prepare-rollback.yml`로 세 서버의 **실행 중인 이미지 ID**를 각각 `doyeon-app:rollback`에 보존했다.
- 로컬에서 `linux/amd64` 이미지를 빌드해 세 VM의 Docker에 로드했다. Jenkins 이미지 Push 경로와 달리 VM의 기존 이미지 태그 검사 후 로컬 이미지를 사용했다.

## 정상 배포 결과

`canary-rolling.yml`에 `image_ref=doyeon-app:canary-live-20261021`, `app_version=v3`, `release_id=v3-canary-live-20261021`, `rolling_batch_size=1`, 직전 릴리스 `v2-8`을 전달했다.

1. Nginx 가중치를 앱1 `1`, 앱2·앱3 각각 `9`로 조정했다. 설정 검사와 reload가 통과했다.
2. 앱1을 upstream에서 제외하고 새 이미지를 실행했다. 직접 `/health`와 `/version`이 첫 시도에 통과해 낮은 가중치로 복귀했다.
3. Nginx 경유 `/health` **60회가 모두 정상**이었고, 새 릴리스 앱1이 **1회** 관찰됐다. 세 서버가 모두 관찰되고 카나리 비율이 20% 이하라는 배포 게이트를 통과했다.
4. 앱2, 앱3을 순서대로 배포했다. 두 서버 모두 직접 검사가 첫 시도에 통과했다. 마지막으로 세 upstream 줄을 기본 가중치로 복원했다.
5. 별도 `verify.yml`에서 앱 서버 3대 직접 `/health`, Nginx `/health`, 세 upstream 줄 검사가 모두 통과했다. 최종 릴리스는 `v3-canary-live-20261021`이다.

배포 전후를 포함한 LB `/version` 연속 요청 926회에서 HTTP 실패는 **0회**였다. 카나리만 새 버전이던 혼합 구간(첫 앱1 `v3` 응답부터 첫 앱2 `v3` 응답 직전)에는 351회 중 앱1의 새 버전 응답이 24회(**6.8%**)였다. 가중치로 계산한 기대 비율 `1/(1+9+9) ≈ 5.3%`와 차이가 나는 이유는 실제 요청·Nginx 워커 분산에 따른 표본 변동이다. 전체 원본은 [정상 배포 요청 CSV](results/normal-rollout-20261021.csv)에 저장했다.

## 장애 주입과 롤백 결과

정상 `v3` 릴리스를 세 서버에 다시 보존한 뒤, `/health`가 의도적으로 HTTP 503을 반환하는 `v4-canary-health-fail-20261021` 이미지를 배포했다.

- 앱1의 직접 `/health`가 **12회 모두 HTTP 503**으로 실패했다. `rolling.yml`은 여기서 중단했고 앱2·앱3의 컨테이너는 교체하지 않았다. 검증되지 않은 앱1은 upstream에서 제외된 상태였다.
- 배포 종료 코드 `2`를 감지한 로컬 실행 스크립트가 즉시 `rollback.yml`을 호출했다. 롤백은 세 서버의 보존 이미지를 다시 실행하고 직접 `/version`, Nginx `/version` 및 기본 가중치 줄을 확인했다. 모든 호스트의 `failed=0`으로 완료됐다.
- 이어서 `verify.yml`로 세 앱 서버 직접 `/health`, LB `/health`, 기본 upstream 줄을 확인했다. 모두 정상 `v3-canary-live-20261021`이었다.

## Timeout·Retry·요청 분산 설정 근거

배포 전 세 VM의 로컬 `/health`를 각각 100회 측정했다. 이 표본은 정상 상태의 짧은 관찰이며 장기간 p99.9나 실제 앱 시작시간 분포를 대신하지 않는다.

| VM | p50 | p95 | p99 | 최대 |
| --- | ---: | ---: | ---: | ---: |
| 앱1 | 0.75ms | 0.91ms | 1.61ms | 24.55ms |
| 앱2 | 0.77ms | 0.99ms | 1.19ms | 24.90ms |
| 앱3 | 0.78ms | 0.93ms | 1.05ms | 24.34ms |

- **HTTP Timeout 3초:** [앱 역할](../../../practice/doyeon/ansible/roles/app/tasks/main.yml)의 직접 `/health`와 `/version` 호출마다 적용한다. 정상 응답의 관측 최대 약 25ms보다 여유를 두면서, 연결이 멈추면 Ansible 기본 소켓 타임아웃 30초를 기다리지 않도록 한 값이다. 앱이 준비되지 않아 연결이 거부되거나 503을 반환하는 경우에는 호출이 즉시 끝날 수 있다.
- **최대 12회 시도, 5초 간격:** 새 컨테이너의 준비 시간을 약 1분까지 허용하는 기존 정책을 유지했다. `retries: 12`는 이 환경의 Ansible에서 **최초 시도를 포함한 최대 12회**임을 실제 실패 로그의 `attempts: 12`로 확인했다. 503이 즉시 반환되면 시도 사이 대기만 약 `11 × 5 = 55초`; 각 요청이 3초를 모두 쓰는 단순 상한은 `12 × 3 + 11 × 5 = 91초`에 작업 오버헤드가 더해진다. 실제 장애 배포 전체는 99초가 걸렸다. 정상 앱은 세 서버 모두 첫 Health Check에 성공했다.
- **동시 재시도 제어:** 카나리는 앱1 한 대, 잔여 롤링은 기본 배치 크기 1대이므로 배포 후 Health Check는 서버별로 순차 수행된다. 각 호출은 해당 VM의 `127.0.0.1`을 향해 공용 LB에 재시도 부하를 주지 않는다. Docker Hub처럼 **공유 대상**을 향하는 이미지 Pull 단계에는 실험 후 `serial: 1`을 추가해 세 VM이 동시에 같은 간격으로 재시도하지 않도록 했다. 이 변경은 Ansible 문법 검사까지 완료했으며, 실제 Docker Hub Pull 경로는 이번 실험에서 실행하지 않았다. 이 3대 실습에서는 별도 무작위 Jitter를 넣지 않았다. 더 많은 서버가 동시에 같은 공유 서비스를 호출한다면 백오프·Jitter와 전체 재시도 예산을 다시 설계해야 한다.
- **카나리 관찰:** LB 경유 60회 요청은 `verify-canary.yml`의 순차 반복이다. 모든 응답의 릴리스·인스턴스를 검사하고, 새 버전 노출을 확인하면서 앱1 비율이 20%를 넘으면 확대를 중단한다. 60회 표본의 비율은 장기 트래픽 비율을 보증하지 않으므로 연속 요청 CSV도 함께 기록했다.

## 검증 범위와 남은 확인

이번 실행은 **실제 VM의 배포·실패 중단·Ansible 롤백**을 확인했다. Jenkins Job이 새 코드를 읽게 하려고 `origin/week8/doyeon`으로 푸시하려 했으나, 자동 승인 검토가 **해당 저장소로 코드 게시를 승인한 근거가 부족하다**는 이유로 거절했다. 이 거절을 우회하지 않았다. 따라서 Jenkins의 `post.failure`가 실제로 자동 호출하는 경로, Docker Hub Push 경로, Discord 알림은 이번 실행에서 검증되지 않았다. 실험에 사용한 배포 코드는 로컬 커밋 `8752c2e`에 있으며 원격에는 게시되지 않았다. Jenkins 통합 검증에는 이 코드를 Jenkins가 읽는 Git 브랜치에 게시하는 승인이 필요하다.
